## 1. Executive Summary

본 문서는 TheKIE의 **Lucia 가상공유거래 정산 플랫폼** 프로토타입(MVP) 개발에 필요한 기능 요구사항을 정의한다. 12주 안에 LH 본사 ESG 경영실에 시연 가능한 동작 시스템을 구축하여, M+6 RE100 출자 MOU 체결의 결정적 마일스톤을 뒷받침하는 것이 목표다.

### 1.1 핵심 가치 제안

본 프로토타입은 5가지 비즈니스 가치를 증명한다.

- **기술 가능성**: 블록체인 기반 다자 정산이 실제로 작동하며, LH 명시 "가상공유거래 기술 실증" 요구를 직접 충족한다.
- **투명성**: 1 kWh 발전이 어떻게 분배되는지 1,643세대 LH 입주민·280세대 국민임대·916세대 소외계층까지 추적 가능하다.
- **운영 효율**: 116동을 단일 대시보드에서 통합 관리하여 LH·지자체·민간 운영 부담을 자동화한다.
- **감사 대응**: 변조 불가 원장으로 공공기관 감사·CBAM 보고·RPS 의무 이행을 자동 증명한다.
- **확장성**: 9,354동까지 선형 확장 가능한 아키텍처를 부하 테스트로 검증한다.

### 1.2 기능 요구사항 분포 *(v1.2 갱신)*

본 문서는 **32개 기능 요구사항을 7개 도메인**으로 구분하여 정의한다.

## 2. 사업 배경 및 시스템 목적

### 2.1 사업 배경

LH는 2025년 9월 울진군과 매입임대 햇빛발전소 협약을 체결하여, 116개 다가구주택 옥상에 3 MW 태양광 설비를 구축하고 20년 동안 발전수익의 약 41%(66억원)를 입주민·소외계층 주거비로 환원하는 ESG 모델을 시작했다. LH 사업자료(PDF Slide 4)는 이 사업의 핵심 차별화 요소로 다음을 명시한다.

> **[LH 명시 요구]** 「미래 신기술인 가상공유거래(Virtual Power Sharing)에 대한 기술 실증의 공공성 확보」

"가상공유거래"는 한국에서 표준화되지 않은 신기술로, 1동의 옥상에서 발전된 전력이 물리적으로 가까운 한전 변전소로 흐르더라도, 회계·인증 차원에서 LH 입주민·소외계층·RE100 기업 등 다수 주체에게 분배되는 메커니즘이다. 이를 자동화하려면 다자 정산, 변조 불가 원장, 다중 외부 시스템 연동이 필수이며, 이는 본질적으로 블록체인 기반 정산시스템이 가장 적합하다.

### 2.2 시스템 목적

본 프로토타입은 다음 3가지 목적을 수행한다.

- **목적 1 — LH 채택**: M+3 LH 본사 시연을 통해 Lucia를 "공식 정산 플랫폼"으로 자리매김. 향후 ReSCO·VPP·햇빛소득마을 사업이 Lucia와 인터페이스해야 하는 표준 지위 확보.
- **목적 2 — RE100 컨소시엄 확보**: M+6 SPC 설립 합의를 위해 RE100 기업(SK·삼성·네이버·기아 등)에 "출자 시 받게 될 정산 투명성"을 시각적으로 증명.
- **목적 3 — 기술적 검증**: 9,354동 확장 시 시스템이 선형으로 작동하는지 부하 테스트로 검증. 후속 단계 투자·개발 의사결정에 필요한 기술적 신뢰성 확보.

### 2.3 시스템 범위

본 프로토타입은 "실제 운영 시스템"이 아니라 "가상공유거래 정산이 가능함을 증명하는 시연 시스템"이다. 따라서 신뢰성·확장성·보안보다 "이해 가능성"과 "시연 임팩트"를 우선한다.

| ✓ In-Scope (MVP) | ✗ Out-of-Scope (Phase 2 이연 — §12 참조) |
|---|---|
| 116동 발전 데이터 시뮬레이션 | 실제 IoT 센서 H/W 통합 |
| Lucia 블록체인 정산 엔진 (Hyperledger Fabric) | Mainnet 배포 (Pilot은 Local/Testnet) |
| 28개 정산 항목 중 핵심 9개 화폐 흐름 | CBAM·K-ETS·VPP 통합 (Mock만) |
| KIE-REMS Lite 모니터링 대시보드 | Full SaaS 다중 테넌트 아키텍처 |
| KPX·한국에너지공단 Mock API | 실제 KPX 도매시장 API 연동 |
| LH 본사 시연용 데모 시나리오 | ISMS-P 인증 (병행 추진하나 별도 트랙) |

## 4. Use Case 개요

본 프로토타입의 핵심 Use Case 5개를 정의한다. 각 UC는 사용자 관점에서 "무엇을 할 수 있는가"를 기술하며, 6~9장의 기능요구사항(FR)이 이를 구현한다.

### UC-1: 1 kWh 발전 → 28개 정산 항목 자동 분배

- **사용자**: 시스템 자동 트리거 (사용자 개입 없음)
- **시나리오**: Uljin 116동 중 1동(예: ULJN-001)에서 1.2 kWh 발전 이벤트가 발생하면, Lucia가 자동으로 SMP 매출, REC 적립, 가상공유거래 분배(LH 입주민 64.2% / 국민임대 10.9% / 소외 35.8%), SaaS 수수료, O&M 비용 등 9개 화폐 항목과 6개 인증서 항목을 계산하여 블록체인에 기록한다.
- **관련 FR**: FR-S-001 ~ FR-S-006, FR-X-001

### UC-2: LH 본사 담당자가 정산 결과를 검증한다

- **사용자**: LH ESG 경영실 담당자
- **시나리오**: KIE-REMS 대시보드에 접속하여 특정 동·기간을 선택하면, 해당 기간의 발전량·SMP 매출·REC 적립·주거비 환원이 시각화된다. 임의의 정산 기록을 선택하여 블록체인 트랜잭션 ID·해시·타임스탬프 확인이 가능하며, 변조 시도 시 즉시 거부된다.
- **관련 FR**: FR-M-001, FR-M-003, FR-S-007, FR-S-008

### UC-3: SPC 운영자가 116동 통합 모니터링한다

- **사용자**: SPC 운영팀
- **시나리오**: 대시보드 메인 화면에서 116개 동 전체의 발전량, 이상 알림, 누적 정산 금액을 한눈에 확인. 동별 클릭 시 상세 화면으로 진입하여 시간별 발전량 차트, 인버터 상태, 최근 정산 이력을 확인. 이상 감지 시 자동 알림 발송.
- **관련 FR**: FR-M-001, FR-M-002, FR-M-005, FR-M-006, FR-D-002

### UC-4: 입주민이 자기 환원 내역을 조회한다

- **사용자**: LH 매입임대 / 국민임대 / 에너지소외 입주민 (FR-A-001 `resident` 역할로 로그인)
- **시나리오**: 로그인 surface에서 데모 계정 선택 → `RoleRedirect` 가 `/portal/:user_id` 로 안내 → 본인의 월별 환원 금액(예: 6,420원)이 어떻게 계산되었는지 확인. 어느 동의 발전량에서 얼마가 분배되었는지 추적 가능. 분쟁 시 블록체인 증빙 자료를 PDF로 다운로드 가능. URL-token 우회 경로는 v1.2 시점에 사칭 위험으로 제거됨 (`7fbf432`).
- **관련 FR**: FR-A-001 (인증), FR-M-007 (포털 본문), FR-S-005, FR-O-002

### UC-5: 9,354동 확장 시뮬레이션

- **사용자**: 시스템 부하 테스트 (자동)
- **시나리오**: 116동 → 1,000동 → 9,354동으로 시뮬레이션 데이터를 점진적으로 늘리며, 정산 처리 시간·대시보드 응답 속도·블록체인 트랜잭션 처리량을 측정. 9,354동 부하에서도 응답 시간 5초 이내 유지를 검증.
- **관련 FR**: FR-O-001, NFR-1, NFR-3

## 5. 기능 요구사항 — 정산 도메인 (FR-S)

Lucia 정산 엔진의 핵심 기능을 정의한다. 본 도메인은 시스템의 차별화 가치가 응축된 영역이며, **9개 기능 모두 "Must Have"**다 *(v1.0의 12건 중 S-010/011/012는 v1.1에서 §12로 이연)*.

### FR-S-001 — 발전 이벤트 수신 및 검증

| 항목 | 내용 |
|---|---|
| 우선순위 | **Must Have** |
| 설명 | IoT Gateway로부터 받은 발전 이벤트(building_id, timestamp, kWh)를 검증하여 정산 처리 큐에 추가한다. |
| 입력 | `{ building_id: string, timestamp: ISO8601, kwh: number(0~10000), source: 'simulator'\|'real' }` |
| 처리 | 1) building_id 존재 여부 검증 (등록된 116개 동 중 하나) 2) timestamp 미래 시점 거부 3) kwh 음수·비정상값(>1000) 거부 4) Redis Queue에 enqueue (FIFO) |
| 출력 | 검증 통과 시 event_id 반환 / 실패 시 HTTP 400 + 오류 코드 |
| 검증 기준 (AC) | 유효 입력 100건 처리 시 100% 큐 추가 / 비정상 입력 100% 거부 / 처리 시간 50ms 이내 |

### FR-S-002 — SMP 매출 계산

| 항목 | 내용 |
|---|---|
| 우선순위 | **Must Have** |
| 설명 | 발전 이벤트의 kWh × 시간대별 SMP 단가를 계산하여 SPC 매출로 적립한다. |
| 입력 | 발전 이벤트 (kwh, timestamp) + KPX Mock API 호출 (시간대별 SMP) |
| 처리 | 1) 시간대별 SMP 조회 (예: 2026-04-30 13:00 → 119원/kWh) 2) `revenue = kwh × smp_price` 계산 3) settlements 테이블에 기록 |
| 출력 | `{ smp_revenue: number(원), smp_price: number, kwh: number }` |
| 검증 기준 (AC) | 1.2 kWh × 119원 = 142.8원 정확히 계산 / 소수점 둘째 자리 반올림 |

### FR-S-003 — REC 발급 및 가중치 적용

| 항목 | 내용 |
|---|---|
| 우선순위 | **Must Have** |
| 설명 | RPS 운영지침에 따라 REC 가중치(지붕형 1.0 + 주민참여형 0.2 = 1.2)를 적용하여 REC를 발급한다. |
| 입력 | 발전 이벤트 (kwh) + 동 정보 (지붕형·주민참여형 분류) |
| 처리 | 1) 가중치 조회 (Pilot은 모든 동 1.2) 2) `rec_amount = (kwh ÷ 1000) × weight` 계산 (1 REC = 1 MWh) 3) REC 발급 트랜잭션 블록체인 기록 4) 한국에너지공단 Mock API에 발급 보고 |
| 출력 | `{ rec_amount: number, weight: 1.2, rec_value: number(원) }` |
| 검증 기준 (AC) | 1.2 kWh × 1.2 = 0.00144 REC. 70,000원/REC 기준 약 100원 매출 적립 |

### FR-S-004 — 가상공유거래 분배 계산

| 항목 | 내용 |
|---|---|
| 우선순위 | **Must Have ★ (BM 핵심 차별화 — 가설 2)** |
| 설명 | 발전수익을 LH 입주민·국민임대·소외계층 3개 그룹에 비례 분배한다. 본 BM의 핵심 차별화 기능. |
| 입력 | Year 1 매출 = SMP + REC × 가중치 / Beneficiary 테이블의 share_ratio |
| 처리 | 1) 발전수익의 41%(주거비 환원 비율)를 분배 대상으로 산출 2) 3개 그룹 비율 적용: LH 매입임대 64.2% (1,643세대) / 국민임대 10.9% (280세대) / 에너지소외 35.8% (916세대) 3) 각 세대별 환원 금액 계산 4) 분배 결과 블록체인 기록 |
| 출력 | `{ housing_subsidy_total, by_group: [{ group, ratio, amount, household_count, per_household }] }` |
| 검증 기준 (AC) | 분배 합계 = 발전수익 × 41% ± 0.1% / 3개 그룹 합 = 100% / 세대별 금액 = 6,420 / 7,420 / 18,195원 ± 1원 |

- **가정 1**: LH 본사 ESG 경영실이 M+3 시연 일정을 수락한다 (사전 약속 필요)

- **가정 4**: Hyperledger Fabric 라이선스 무료 사용 (Apache 2.0, 상업 사용 가능 확인)
